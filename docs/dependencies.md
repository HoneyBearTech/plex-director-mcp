# Dependencies and vulnerability management

This page says how Plex Director chooses, obtains and tracks the software it depends on, and how findings
from dependency scanning (software composition analysis, SCA) and from static analysis of its own code
(SAST) are handled. Reporting a vulnerability in Plex Director itself is covered by
[SECURITY.md](../SECURITY.md).

## Choosing a dependency

A new dependency is added only when it clearly beats writing and maintaining the code here. The backend
has nine runtime dependencies, and keeping that number small is deliberate (the test suite, for example,
uses Node's built-in runner rather than a framework). Before adding one, the pull request says why, and
the dependency must:

- be actively maintained (recent releases, responsive to security reports) and widely used, or small
  enough to review;
- prefer the official SDK where one exists (the MCP SDK, the Anthropic SDK);
- have a license compatible with the project's MIT license (MIT, ISC, BSD, Apache-2.0 or similar
  permissive licenses);
- come from the standard registry (npm, Docker Hub or the distroless images on `gcr.io`, GitHub Actions
  from their authors);
- not duplicate something already in the tree or in Node itself.

## Obtaining dependencies

Every dependency is declared in a manifest and pinned in a lockfile, and installed with the ecosystem's
standard tool; nothing is copied into the repository ("vendored").

| What | Declared in | Pinned by | Installed with |
| --- | --- | --- | --- |
| Backend (Node.js) | `package.json` | `package-lock.json` (versions and integrity hashes) | `npm ci` |
| Dashboard (React) | `web/package.json` | `web/package-lock.json` (versions and integrity hashes) | `npm ci` |
| Container base images | `Dockerfile` (`node:*-slim` for the build stages, `gcr.io/distroless/nodejs24-debian12` for the runtime) | image digests (`@sha256:…`) | Docker |
| CI actions | `.github/workflows/*.yml` | full commit SHAs, with the version in a comment | GitHub Actions |

The packages whose install scripts are expected to run are listed, with exact versions, under
`allowScripts` in `package.json` (`better-sqlite3`, `esbuild` and `fsevents`). The build stages install a
compiler toolchain from Debian with `apt-get` for those native modules; it is not present in the runtime image,
which has no package manager.

## Tracking dependencies

- **Dependabot** (`.github/dependabot.yml`) opens update pull requests **weekly** for the backend's npm
  dependencies, the dashboard's npm dependencies (`/web`), the Docker base images and the GitHub Actions,
  and security updates as soon as an advisory appears. Minor and patch updates are grouped into one pull
  request per ecosystem.
- **Auto-merge** (`.github/workflows/dependabot-auto-merge.yml`): Dependabot's minor and patch updates
  to npm packages and the Docker base image merge automatically, but only once all required checks on
  `main` pass. Major updates, GitHub Actions updates (GitHub doesn't let the workflow token enable
  auto-merge on a pull request that edits workflow files), and major Node.js base image bumps (which
  Dependabot ignores, because the build and runtime images must move together) wait for the maintainer.
  `docker/scout-action` is held below 1.25, which rejects the current Docker Hub token.
- **Every push and pull request** runs `npm audit --audit-level=high` on both npm projects in the `check`
  job of `.github/workflows/ci.yml`. A high or critical advisory anywhere in either locked dependency tree
  fails CI, which blocks merging (including Dependabot's own pull requests).
- **Dependency review** (`.github/workflows/dependency-review.yml`) blocks a pull request that adds or
  changes a dependency with a known vulnerability of moderate or higher severity, or with a license outside
  the allowlist (MIT, Apache-2.0, BSD, ISC and similar permissive licenses; MPL-2.0; CC-BY-4.0 and OFL-1.1
  for data and fonts).
- **Secret scanning** (`.github/workflows/secret-scan.yml`) runs gitleaks over the commits of every push and
  pull request, with matches redacted from the log.
- **An SBOM** (SPDX, generated by Docker BuildKit) is attached to every published image as an attestation,
  so the exact packages in a release can be listed; see [verifying releases](verifying-releases.md).
- **CodeQL** (`.github/workflows/codeql.yml`) analyses the TypeScript on every push, every pull request and
  weekly, so newly published queries are run against unchanged code.
- **OpenSSF Scorecard** (`.github/workflows/scorecard.yml`) scores the repository's supply-chain practices
  weekly and on every push to `main`; results appear in code scanning and on the README badge.
- **Docker Scout** scans each published image for critical and high vulnerabilities and reports them in the
  job summary. It does not block publishing yet.
- **GitHub's dependency graph** and Dependabot security alerts watch the default branch between changes.

## Policy for vulnerabilities in dependencies

These targets are for published advisories in the libraries and base images Plex Director uses, which
usually only need a version bump. Vulnerabilities reported in Plex Director's own code follow the process
and timelines in [SECURITY.md](../SECURITY.md).

Severities are the advisory's CVSS rating. "Fixed" means the vulnerable version is no longer used on
`main` and, if a release is affected, a patched image is published.

| Severity | Remediation threshold |
| --- | --- |
| Critical | within 14 days of the finding |
| High | within 14 days |
| Medium (moderate) | within 60 days, or with the next release if sooner |
| Low | with the next regular dependency update |

- A finding can be closed without an upgrade only if the vulnerable code cannot be reached from Plex
  Director. That decision is written down in the pull request or advisory that closes it, with the reason.
- If no fixed version exists, the maintainer mitigates (configuration, removing the feature that uses it,
  or replacing the dependency) within the same threshold, or records why it is not exploitable.
- **Malicious packages** are removed at once, and any image that contained one is withdrawn and announced.
- Because CI fails on any high or critical advisory, a new one usually surfaces within days as a failing
  check on the next pull request, and is fixed before anything else merges.

**Recent example.** On 2026-10-15, [PR #66](https://github.com/HoneyBearTech/plex-director-mcp/pull/66)
fixed two high-severity advisories that had started failing the audit step on every open Dependabot pull
request:
[GHSA-6qxp-vccf-f47h](https://github.com/advisories/GHSA-6qxp-vccf-f47h) (`@modelcontextprotocol/sdk`,
upgraded from 1.30.0 to 1.32.1) and [GHSA-68fv-2mgg-jv7q](https://github.com/advisories/GHSA-68fv-2mgg-jv7q)
(`source-map-js` in the dashboard's build tooling, upgraded from 1.2.1 to 1.2.2).

## Before a release

A version tag (`v*.*.*`) is only pushed when, at that commit:

- `main` has no open dependency finding past its remediation threshold;
- the required CI checks, including both dependency audits and the image smoke test, passed;
- the image is published to both registries and signed by the same workflow run.

## Policy for findings from static analysis (SAST)

Plex Director's own code is analysed by CodeQL on every pull request and by the TypeScript compiler's type
checks as part of the required checks.

| Finding | Threshold |
| --- | --- |
| CodeQL alert of high or critical severity | fixed before merging |
| Any other CodeQL alert on a pull request | fixed before merging, or dismissed with a written reason |
| TypeScript type error | blocks the merge (CI fails) |

A finding is dismissed only when it is a false positive or cannot be exploited, and the reason is recorded
in the dismissal. Alerts found on `main` by the weekly scan follow the dependency thresholds above. Past
CodeQL findings fixed this way include incomplete sanitisation of Markdown table cells (`escapeTableCell`
in `src/util.ts`) and un-rate-limited file-system access by the static file handlers (the global rate
limiter in `src/web/app.ts`).

## Published vulnerabilities

Vulnerabilities in Plex Director itself are reported privately as described in
[SECURITY.md](../SECURITY.md) and, once fixed, published as
[GitHub security advisories](https://github.com/HoneyBearTech/plex-director-mcp/security/advisories) with
the affected and fixed versions and how to upgrade or mitigate.
